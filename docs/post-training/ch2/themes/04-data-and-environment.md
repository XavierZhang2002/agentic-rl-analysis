# 2.4 数据与环境工程

!!! abstract "本节摘要"
    2025 年的说法是"数据飞轮是终局"；2026 年要改成**环境飞轮**——瓶颈不在有多少 token，而在有多少**可执行、可验证、可复现**的环境。本节整理环境类型、四条合成路线、质量控制（含一个最隐蔽的坑：环境数据库不一致），以及"环境飞轮"的当前证据。

---

## 一、为什么是环境，不是数据

推理 RL 的数据可以从题库里拿（数学题、代码题），但 agent 的训练数据必须**与环境交互**才能产生：

- 真实环境（API、网页、IDE）成本高、延迟大、不可逆；
- 合成环境可控，但**逼真度**决定泛化性；
- 更要命的是：**环境不可靠时，正确解会被判为失败**——这比没有数据更糟。

所以 2026 年的投入重心从"造数据"转向"造环境 + 造验证器"。

## 二、环境类型与代表

| 类型 | 代表 | 规模/特点 |
|---|---|---|
| **SWE（代码库修复）** | GLM-5 的 >1 万可验证 SWE 任务；Kimi K3 的 DeepSWE | 需要仓库级上下文与测试 |
| **Terminal（终端）** | GLM-5 的 Harbor 格式、Docker 构建精度 >90% | 任务可复现、可容器化 |
| **Search（检索）** | GLM-5 用 200 万+ 网页构建 Web 知识图谱 | 多跳、需要上下文管理 |
| **Web/交互** | Qwen3.8-Max 的 Workspace 轴；可交互网页任务 | 需要浏览器沙箱 |
| **微虚机沙箱** | Kimi K3 的 AgentENV（Firecracker） | checkpoint/resume 133/49 ms，累计 5,121 万 sandbox |
| **合成环境（自动生成）** | EnvFactory（[2605.18703](https://arxiv.org/abs/2605.18703)）、SPADE（[2608.19197](https://arxiv.org/abs/2608.19197)）、AutoEnvScaling（[2610.14163](https://arxiv.org/abs/2610.14163)） | 自动构造可执行工具环境 + 轨迹 |

## 三、四条合成路线

1. **Seed-then-Expand**：从真实工具链出发，BFS 受控扩张（LongCat 的做法）——**不是**随机注入工具节点。
2. **自动造环境**：AutoEnvScaling 让终端 agent 自己造环境，报出约 **25×** 的有效环境率（相对人工）。
3. **自博弈共演化**：SPADE 让"环境设计器"与"agent"互相出题，用 regret 驱动难度。
4. **微虚机复用**：Kimi K3 用 Firecracker 把环境启动压到毫秒级，才撑得起 1M 上下文的 agentic RL。

## 四、质量控制：一个最隐蔽的坑

!!! danger "环境数据库不一致会制造有偏的负奖励"
    美团 LongCat 团队公开的经验：盲目给环境注入随机工具节点，会触发**未满足依赖的级联失败**、破坏跨工具的数据库一致性。后果是——**正确解执行失败，被判为失败，模型因此学到"这样做不对"**。

    这是 agentic RL 数据侧最难发现的污染源：它不报错、不降指标，只是静默地把正确行为标成错误。

**对策**：沿原可执行工具链做 BFS 受控扩张；每次扩张后跑"已知正确解"回归测试。

其余三条质量控制：

- **可解性检查**：环境上线前必须确认存在至少一条可解路径（GLM-5.3 的 judge agent）。
- **验证器三检**：正确解给分 / 空操作不给 / 未完成不给（见 [2.3](./03-reward-lineage.md)）。
- **去污染**：评测集与训练集的重叠检测，尤其是公开 benchmark。

## 五、从数据飞轮到环境飞轮

| 2025 的说法 | 2026 的证据 |
|---|---|
| 模型自己生成训练数据（Self-Rewarding） | 仍然有效，但只解决"有数据"，不解决"有新任务" |
| 数据配比是核心 | 配比仍重要，但头部厂商转向"环境多样性" |
| 数据飞轮是终局 | **环境飞轮**：环境生成器与 solver 共演化（SPADE、AutoEnvScaling） |

**当前最接近"递归自我改进"的证据**：proposer（出题/造环境）与 solver（解题）的共演化——注意是"接近"，不是"实现"。

## 六、决策表

| 你的场景 | 建议 |
|---|---|
| 有真实 API/工具 | 优先用真实环境，合成环境只做兜底 |
| 没有真实环境 | 用 EnvFactory 类工具自动构造，再做可解性检查 |
| 环境已有一批 | **先做一致性回归测试**，再谈扩容 |
| 需要长程任务 | 微虚机 + checkpoint/resume，否则启动开销吃掉训练效率 |
| 评测集与训练集可疑 | 先做去污染，否则所有指标都不可信 |

## 开放问题

1. **环境的"逼真度"如何度量**：目前只有下游泛化作为间接指标，没有直接度量。
2. **环境规模的上限**：AutoEnvScaling 报 25×，但环境越多，验证成本也线性增长——是否存在最优规模？
3. **环境与验证器能否一起自演化**：SPADE 只共演化环境与 solver，验证器仍是人工设计。
