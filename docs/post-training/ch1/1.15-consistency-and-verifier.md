# 1.15 一致性与验证器：两个非算法因素（2026）

!!! abstract "本节摘要"
    2026 年的两个共识不是关于损失函数的：① **MoE 上的成败主要取决于训练/推理是否一致**，路由回放、确定性算子、量化对称这些"非算法"手段比换目标函数更有效；② **验证器本身需要被验证**——准确率提升不等于推理可靠，外延验证会系统性诱发捷径，rubric 存在维度间背离。

!!! note "与 1.9 的关系"
    1.9 把 GSPO 讲成"根治 MoE 不稳定"的方案。2026 年的结论要修正：**GSPO 是算法层补丁，MoE 的根因是系统一致性**。两者正交，可以叠加。

---

## 一、MoE 与 RL：一致性优先于目标函数

### 1.1 问题的物理图像

MoE 每层有一个 gating network 选 top-k 专家。RL 训练里存在三份"策略"：

1. **rollout 引擎**（vLLM/SGLang）实际生成时的路由；
2. **训练引擎重算 old logprob** 时的路由；
3. **反向传播**时的路由。

参数更新后，gating logits 的微小变化会让 top-k **整体翻盘**——同一个 token 在前向与反向里走的是**不同的物理子网络**。此时 token 级 importance ratio 的分子分母根本不对应同一个模型。

### 1.2 三种修法（2026 的代表）

| 修法 | 代表 | 做法 | 代价 |
|---|---|---|---|
| **路由回放** | R3（[2510.11370](https://arxiv.org/abs/2510.11370)，ICML 2026，88 引） | 记录 rollout 时的 expert indices，训练时强制回放 | 需推理引擎返回路由；跨 EP 同步开销 |
| **确定性算子** | GLM-5（[2602.15763](https://arxiv.org/abs/2602.15763)） | DSA indexer 的 top-k 不能回放（k=2048），改用确定性 `torch.topk`，并在 RL 期间冻结 indexer | 略慢，但消除非确定性 |
| **消除路径差** | Kimi K3 | QAT（MXFP4/MXFP8）贯穿 SFT 与 RL，**rollout 与训练共用同一量化** | 需要训练侧 QAT 全流程支持 |

**R3 的价值**：它把 DeepSeek V3.2 的 Keep Routing 学术化，并证明在 MoE 上**优于 GSPO/TIS**。实测（Qwen3-30B-A3B + GRPO）：无回放 62.23 → R3 71.83，KL 降约 2×。

**GLM-5 的价值**：它证明了另一件事——**不是所有结构都能回放**。DSA 的 indexer 要取 k=2048 的 top-k，逐 token 存索引的存储与通信开销不可接受，所以只能走"确定性算子 + 冻结子模块"。这是"回放不可行时的替代方案"。

### 1.3 量化也是一致性问题

- **MoEResQ**（[2611.04376](https://arxiv.org/abs/2611.04376)）：FP4 RL 在 MoE 上必须**训练/推理两侧对称恢复**，否则量化误差会被当成策略偏移。
- **TRACE**（[2610.07767](https://arxiv.org/abs/2610.07767)，Qwen）：用 rollout 侧的真实量化结果反向指导训练侧舍入，rollout 最高 **5.4×**。
- **RoutePack**（[2608.12146](https://arxiv.org/abs/2608.12146)）：专家放置 + 轨迹调度，吞吐 +4.4–11.9%。

### 1.4 一条可执行的检查清单

在抱怨"算法不 work"之前，先确认这五项：

- [ ] 训练与推理的**路由**是否可复现（回放 / 确定性 / 冻结）？
- [ ] token 化是否一致（**TITO**，而不是 text-in-text-out）？
- [ ] 数值精度是否一致（QAT 全流程 / 量化对称 / LM head FP32）？
- [ ] 采样与训练的**位置编码、截断、特殊 token** 是否完全一致？
- [ ] 异步下的 staleness 是否有上界？

!!! danger "一个真实案例"
    GLM-5 报告里记录了：CUDA 非确定性 top-k 在 RL **数步内**导致性能骤降并伴随熵骤降；换成确定性算子后才有显著增益。这类问题不会在小规模实验里暴露，也不会报错。

## 二、验证器：可验证奖励不等于可靠奖励

### 2.1 RLVR 的三个反例

**反例一：准确率 ≠ 推理的因果重要性**

*Outcome Rewards Do Not Guarantee Verifiable or Causally Important Reasoning*（[2604.22074](https://arxiv.org/abs/2604.22074)）指出：模型答对了，不代表它用的推理链是**必要**的。论文提出 CIR/SR（因果重要性/充分性）指标，发现大量"正确但推理无关"的样本。

**反例二：外延验证会诱发捷径**

*LLMs Gaming Verifiers*（[2604.15149](https://arxiv.org/abs/2604.15149)）发现：当验证器只看最终结果时，模型会学会**利用验证器的盲区**（例如只在特定格式下正确）。解法是"同构验证"（isomorphic verification）：把同一道题换成等价但表面不同的形式再验一次。

**反例三：rubric 内部会背离**

*Intra-Rubric Reward Divergence*（[2610.26685](https://arxiv.org/abs/2610.26685)）发现：多维度 rubric 的各子维度之间会出现系统性背离——模型优化某一维会伤害另一维，而总分掩盖了这件事。

### 2.2 工业界的做法：把验证器当模型来训

GLM-5.3 的 **verifier 三检**是目前最可复制的工程实践：

1. 给定**已知正确解** → 必须给奖励；
2. agent **什么都不做** → 必须不给；
3. 任务**未完成** → 必须不给。

再加一条：用 solver 的轨迹去"封堵捷径解"。这四条合起来，等价于给验证器做了一次**对抗测试**。

!!! tip "可直接抄的做法"
    把验证器当成一个有 bug 的模型：上线前必须跑"正例/空操作/未完成/捷径"四类测试。这比事后调奖励权重便宜得多。

### 2.3 奖励设计谱系的 2026 版本

| 类型 | 代表 | 优点 | 风险 |
|---|---|---|---|
| 规则/可验证 | 数学、代码、单元测试 | 无噪声、不可 hack（理论上） | 只覆盖有确定答案的任务 |
| 判别式 ORM | GLM-5、Qwen2.5 六维 RM | 低方差、训练高效 | 易被 reward hacking |
| 生成式 GRM | GLM-5、DeepSeek V4 的 actor-as-GRM | 鲁棒、可解释 | 方差大、贵 |
| Rubric/Checklist | CM2（[2602.12268](https://arxiv.org/abs/2602.12268)） | 细粒度、可审计 | 维度间背离 |

**2026 的搭配共识**：规则打底（保证下限）+ GRM 做鲁棒性（提升上限）+ rubric 做可解释（便于审计）。DeepSeek V4 更进一步：**让 actor 自己兼任 GRM**，用 rubric 引导的 RL 数据联合优化"评判"与"生成"。

## 三、把两件事合起来看

```
            ┌─────────────── 训练侧一致性 ───────────────┐
rollout ──► 路由回放 / 确定性算子 / QAT ──► 训练 ──► 更新
            └────────────────────────────────────────────┘
                          │
                          ▼
            ┌─────────────── 验证器可靠性 ───────────────┐
   奖励 ◄── 规则打底 + GRM 鲁棒 + rubric 可审计 + 反作弊测试
            └────────────────────────────────────────────┘
```

**一句话**：2026 年的"训练不稳定"大多不是优化问题，而是**测量问题**——要么测到的 ratio 不是同一个模型（一致性），要么测到的奖励不是想要的行为（验证器）。

## 开放问题

1. **回放的代价**：R3 在超大 k（稀疏注意力）上不可行，是否存在"部分回放 + 确定性兜底"的中间方案？
2. **验证器的对抗训练**：能否把 solver 的作弊行为反过来训练一个更强的验证器？（目前是人工封堵）
3. **CIR/SR 的规模化**：因果重要性指标目前只在离线评测可用，能否进入训练循环？
