    4.2 环境工程：类型、合成与一致性¶

    本节摘要

    2025 年的说法是"数据飞轮是终局"，2026 年要改成环境飞轮：瓶颈不在 token 数量，而在可执行、可验证、可复现的环境数量。本节给出环境类型表、四条合成路线、SWE / Terminal / Search 三类任务的合成方法，以及一个不报错、只静默污染奖励的坑——环境数据库不一致。数据侧的方法论见 4.1 数据工程。

    一、为什么是环境，不是数据¶

    推理 RL 的数据可以从题库里拿（数学题、代码题），agent 的训练数据只能从交互里长出来。三个硬约束把投入重心从"造数据"推向"造环境"：

    • 真实环境贵且不可逆：API、网页、IDE 的调用成本高、延迟大，失败动作无法回滚；
    • 合成环境可控但有偏：逼真度直接决定泛化，模拟轨迹与真实执行存在系统差异；
    • 环境不可靠比没有数据更糟：正确解被判失败时，模型学到的是"这样做不对"——这是负向监督，不是噪声。

    所以 2026 年的投入重心是"可执行、可验证、可复现的环境 + 验证器"：数据可以合成，环境必须先站得住。

    二、环境类型与代表¶

    类型 代表 规模 / 特点
    SWE（代码库修复） GLM-5 的 >1 万可验证 SWE 任务；Kimi K3 的 DeepSWE 需要仓库级上下文 + F2P/P2P 测试
    Terminal（终端） GLM-5 的 Harbor 格式，Docker 构建精度 >90% 任务可复现、可容器化
    Search（检索） GLM-5 用 200 万+ 网页构建 Web 知识图谱 多跳、需要上下文管理
    Web / 交互 Qwen3.8-Max 的 Workspace 轴 需要浏览器沙箱
    微虚机沙箱 Kimi K3 的 AgentENV（Firecracker） checkpoint/resume 133/49 ms，累计 5,121 万 sandbox
    合成环境 EnvFactory（2605.18703）、SPADE（2608.19197）、AutoEnvScaling（2610.14163） 自动构造可执行工具环境 + 轨迹

    前四类决定任务覆盖面，后两类决定吞吐；选型顺序是先真实、后合成，先一致性、后规模。

    规模参考：K2 的工具模拟器在 K8s 上跑到 10K+ 并发；MiniMax Forge 用真实浏览器 / API 跑到 100K+ 并发（Prefix Tree Merging 提速 40×）；V3.2 用 1,827 环境 / 4,417 任务做混合 RL。

    三、四条合成路线¶

    1. Seed-then-Expand（种子扩张）：从真实工具链出发做 BFS 受控扩张，新节点必须挂在已有可执行链上——不是随机注入工具节点；LongCat 用它保住数据库一致性，失败案例见 5.7 LongCat。
    2. 自动造环境：AutoEnvScaling 让终端 agent 自己造环境，报出约 25× 于人工的有效环境率。
    3. 自博弈共演化：SPADE 让"环境设计器"与 agent 互相出题，用 regret 驱动难度，环境随 solver 能力一起变难。
    4. 微虚机复用：Kimi K3 用 Firecracker 把环境启动压到毫秒级（checkpoint/resume 133/49 ms），才撑得起 1M 上下文的 agentic RL。

    前两条解决"环境从哪来"，后两条解决"环境怎么跑得起"；路线可以叠加，但叠加前必须先过一致性检查（见第五节）。

    四、SWE / Terminal / Search 三类数据合成¶

    GLM-5 的 Agentic 数据合成是一条六步流水线：种子任务 → 转成可执行任务（描述 / 上下文 / 工具 / 依赖 / 验证脚本）→ 构建可验证环境 → 执行采集轨迹 → 筛选与修复（正确性、稳定性、exploit、一致性、难度、去重）→ 转训练数据。SFT 保留轨迹（可对错误步骤 mask），RL 只保留任务 + 环境 + 验证脚本；三类任务的差异只在"种子从哪来、验证怎么做"。

    SWE：把一次真实修复重建成可执行任务¶

    • 机制：从真实 GitHub Issue-PR 与 commit diff 出发，重建为"有 bug 的仓库 + 需求描述 + 测试"，模型要自己定位、修改、跑测试，而不是直接输出代码。
    • 验证：F2P（修复前失败、修复后通过）+ P2P（原功能不回归）必须同时满足；缺一，模型要么学不会修复、要么学会破坏原功能。
    • 扩容：SWE-smith（2504.21798）在真实仓库自动注入 bug，一次造 50K 修复任务。
    • 注意：注入 bug 偏单点、易定位，需与真实 Issue 混合，否则模型学的是"修注入 bug"而非"修真实 bug"。

    Terminal：从场景或文档反向生成任务¶

    • 路径 A（真实场景扩展）：种子场景 → 模型生成任务草稿 → agent 落地为标准任务（描述 + Docker 环境 + 测试脚本）→ refine agent 检查修正。
    • 路径 B（技术网页提取）：筛高质量代码 / 命令行网页 → coding agent 自动生成任务 → agent 自验证，不通过就继续改到通过。
    • 工程约束：Docker 构建必须可复现，GLM-5 的 Harbor 格式构建精度 >90%；构建失败会直接变成"正确解被判错"。
    • 注意：路径 B 产出快但任务同质化（都围着网页里的命令转），需按工具 / 领域配平。

    Search：从网页知识图谱造多跳问题¶

    • GLM-5：种子网页不靠人工挑，而是保留早期 search agent 真实访问过的网页；抽实体 / 属性 / 关系建 Web 知识图谱（200 万+ 网页），从低 / 中频实体扩多跳邻域子图，再改写成自然语言问题。
    • 两层过滤：去掉"不搜就能答"和"一次搜索就能解决"的题；再验证答案唯一、证据链闭合、跳转无歧义。
    • MiniMax M2 的 Query 进化：种子实体自主 search / browse → 基于搜索链路生成初始问题 → long-to-short evolution（Removing 去线索 / Obfuscation 模糊化 / Replace 间接描述），进化出没有明显搜索入口的难题。
    • 注意：WKG 的抽取错误会造出"答案唯一但事实错误"的题，比没有题更危险。

    五、质量控制与 LongCat 的数据库一致性坑¶

    环境数据库不一致会制造有偏的负奖励

    美团 LongCat 公开的经验：盲目给环境注入随机工具节点，会触发未满足依赖的级联失败、破坏跨工具的数据库一致性。后果是正确解执行失败、被判失败，模型因此学到"这样做不对"。

    这是 agentic RL 数据侧最难发现的污染源：不报错、不降指标，只是静默地把正确行为标成错误。完整案例见 5.7 LongCat。

    对策：沿原可执行工具链做 BFS 受控扩张；每次扩张后跑"已知正确解"回归测试；把一致性检查设为环境上线门禁。

    检查 做法 缺了会怎样
    可解性 上线前确认至少存在一条可解路径（GLM-5.3 的 judge agent） 全错环境 = 无梯度
    验证器三检 正确解给分 / 空操作不给 / 未完成不给 模型学会空转或半途交差
    测例质量 K1.5：每题 50 组测例 + 10 标答交叉验证（7/10 一致才有效、9/10 通过才入训），1000 题仅 323 题（32%）入训 有效数据量被高估，正确解可能被判错
    去污染 评测集与训练集重叠检测，尤其公开 benchmark 指标虚高，泛化失真
    exploit 检查 能否改测试、读答案文件、绕过验证 奖励被短路，策略不学任务

    六、从数据飞轮到环境飞轮¶

    2025 年的说法 2026 年的证据
    模型自己生成训练数据（Self-Rewarding） 仍然有效，但只解决"有数据"，不解决"有新任务"
    数据配比是核心 配比仍重要，头部厂商转向"环境多样性"
    数据飞轮是终局 环境飞轮：环境生成器与 solver 共演化（SPADE、AutoEnvScaling）

    当前最接近"递归自我改进"的证据是 proposer（出题 / 造环境）与 solver（解题）的共演化——注意是"接近"，不是"实现"。
