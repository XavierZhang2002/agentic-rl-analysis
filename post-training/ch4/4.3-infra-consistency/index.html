    4.3 基础设施与一致性¶

    本节摘要

    Agentic RL 里的"训推不一致"不是小数点后的误差，而是会让奖励优化方向失真的系统性偏差。2026 年头部框架在六个机制上收敛：TITO、双侧 token 级 IS、partial rollout、有界 staleness、全流程 QAT、微虚机。本节先定位四类缺口，再逐个拆机制，然后对比五个框架，最后给出自研/开源判断与五个必看指标。

    一、三份策略，四类缺口¶

    理想情况下，采样与更新用同一个 \(\pi_\theta\)。Agentic 场景实际同时存在三份策略：rollout 引擎（vLLM / SGLang）生成时的策略、训练引擎重算 old logprob 时的策略、反向传播时的策略。三者之间有四类缺口，每一类都有一个已成标配的机制：

    缺口 症状 机制 代表
    token 边界 / 空白 / 截断 训练 loss 正常但效果差 TITO GLM-5、Kimi K3
    数值精度（BF16 vs FP8/FP4） 训练指标正常、部署指标掉 全流程 QAT Kimi K3、TRACE
    离散选择（路由、top-k） ratio 剧烈波动，数步内熵塌 确定性算子 / 路由回放 GLM-5、R3
    策略版本（异步） 同一轨迹前后 token 来自不同版本 双侧 IS + 有界 staleness GLM-5、ASystem

    离散选择这一格最容易被误诊成算法问题。MoE 每层 top-k 在参数更新后可能整体翻盘，同一个 token 在前向与反向走的是不同物理子网络，token 级 ratio 的分子分母根本不对应同一个模型。三种修法：

    1. 路由回放：R3（2510.11370）记录 rollout 时的 expert indices，训练时强制回放。Qwen3-30B-A3B + GRPO 实测 62.23 → 71.83，KL 降约 2×。代价是推理引擎要返回路由、跨 EP 同步有开销。
    2. 确定性算子：GLM-5 的 DSA indexer 每个 token 要取 k=2048 的 top-k，逐 token 存索引不可接受，只能换确定性 torch.topk 并在 RL 期间冻结 indexer。
    3. 消除路径差：Kimi K3 用全流程 QAT 让 rollout 与训练走同一套量化。

    一句话：能回放就回放，不能回放就从源头保证确定性。下文六个机制任何一环缺失，都会在 4.4 的清单里以"静默降分"的形式出现。

    一个真实案例

    GLM-5 报告里记录了：CUDA 非确定性 top-k 让 RL 在数步内性能骤降并伴随熵骤降，换成确定性算子后才有显著增益。这类问题不会在小规模实验里暴露、不会报错，只会让 ratio 悄悄失真。

    二、六个已收敛的机制¶

    六个机制作用在不同层：TITO 在输入层（token 序列本身），双侧 IS 与有界 staleness 在优化层（ratio 与数据新鲜度），全流程 QAT 在数值层，微虚机在执行层；§一 的确定性算子 / 路由回放则专门针对离散选择。任何一层的缺口都不报错，只会让另一层的机制失效。

    1. TITO（Token-in-Token-out）¶

    推理引擎把 token 解码成文本、训练侧再 encode 回去，会在 token 边界、空白/归一化、截断、特殊 token 位置上产生错位——污染单 token 概率估计，且不报错。TITO 让训练侧直接消费推理引擎的 token id 流，中间件记录 token 与元数据。代表：GLM-5 的 TITO Gateway、Kimi K3 的引擎侧直接对接。代价是数据管线必须以 token 为单位，不能自由改 chat template。

    2. 双侧 token 级 IS + clip¶

    异步下一条轨迹生成期间推理引擎可能已更新多次，历史策略无法追踪，于是丢弃 \(\pi_{\theta_{\text{old}}}\)，用 rollout 期间记录的对数概率作行为代理：

    \[ r_t(\theta) = \frac{\pi_\theta(y_t)}{\pi_{\text{rollout}}(y_t)}, \qquad \text{mask}_t = \mathbb{1}\left[r_t \in [1-\varepsilon_l,\ 1+\varepsilon_h]\right] \]

    区间外整 token 屏蔽梯度：不是硬校正所有 off-policy 数据，而是偏差大的不学、偏差小的放心学。代表：GLM-5、SAO（2607.07508）。同源做法是 IcePop：显式区分 \(\pi_{\text{train}}\) 与 \(\pi_{\text{infer}}\)，把 \(\rho=\pi_{\text{train}}/\pi_{\text{infer}}\) 限制在 \([1/\beta,\beta]\) 内，否则置零。两条常被忽略的配套：权重同步后重置 AdamW 一二阶动量；按轨迹记录经历的模型版本序列，最老版本与当前差距超阈值 \(\tau\) 时整条丢弃（freshness control）。

    3. Partial rollout¶

    一条长轨迹不必一次性跑完，按 token 预算切片、边生成边训练；在 1M 上下文、多轮工具调用这种长度方差极大的场景，这是唯一能把 GPU 等待摊平的手段。代表：Kimi K3 的 partial rollout；Ling/Ring 的 ASystem 用全局 token 预算 \(\Phi\) 门控（2606.15079）。配套调度：同一 prompt 的多条 rollout 共享前缀，prefix-tree merging 合并后 40× 加速（Forge）；windowed FIFO 用 \(W=0.3N\) 的窗口在吞吐与分布一致性之间取参；Slime 用 PD 分离 + MTP + 全局 L3 KV cache 压低多轮解码延迟。

    4. 有界 staleness¶

    上界写作 max_staleness × consumer_batch_size，超出即丢弃。LongCat 的 DORA 把 request load ratio 压到 63%——主动放弃 37% 的吞吐换 staleness 可控。异步不是"越快越好"，而是"在一致性约束下尽量快"。 监控看 P99 而非均值：长尾决定稳定性。

    5. 全流程 QAT¶

    把训推不一致从源头消除——训练侧与 rollout 侧用同一套量化。Kimi K3 用 MXFP4 权重 / MXFP8 激活，贯穿 SFT 与 RL。TRACE（2610.07767，Qwen）反过来用 rollout 侧的真实量化结果指导训练侧舍入，rollout 最高 5.4×。补充方向：MoEResQ（2611.04376）要求训练/推理两侧对称恢复，否则量化误差会被当成策略偏移。

    6. 微虚机与环境执行层¶

    环境是 rollout 的一部分，它的启动/恢复延迟直接进端到端成本。Kimi K3 的 AgentENV 用 Firecracker 微虚机，checkpoint/resume 133/49 ms，累计 5,121 万 sandbox；GLM-5 的 Terminal 任务用 Harbor 格式，Docker 构建精度 >90%。

    最小落地顺序¶

    1. TITO：先把 token 对齐，否则后面所有 ratio 都算在错位的分布上。
    2. 确定性算子 + 冻结离散子模块：最便宜、收益最大（GLM-5 的 top-k 案例）。
    3. 双侧 IS + 有界 staleness：开异步的前提；上界没定就别开。
    4. QAT / 微虚机：按需——只有训推量化不同、或长轨迹环境成本高时才必须。

    三、五个框架对比¶

    框架 厂商 核心设计 公开数字
    Forge MiniMax Agent/Gateway + DataPool/Rollout + Train 三模块解耦 10 万+ scaffold；prefix merge 40×；日处理百万级样本
    Slime GLM SGLang 生成 + Megatron 训练；TITO；心跳容灾 1K+ 并发 rollout；INT4 QAT
    DORA LongCat 全流式异步 request load ratio 63%；比同步快 2–4×
    ASystem Ling / Ring partial rollout + 有界 stale 吞吐接近异步、稳定性等同同步
    QwenGyre Qwen 弹性 GPU 重分配 + 轨迹重建/部分打分/去重 700K token/rollout；48 步 NL2Repo 52.5%→58.5%；1.78× 加速

    一个反直觉的数字

    DORA 把 request load ratio 压到 63%，意味着主动放弃约 37% 的吞吐；它的 2–4× 是相对同步基线，不是相对"无限异步"。官方也承认这是控 staleness 的代价。

    四、自研还是用开源¶

    你的情况 建议
    单机 8 卡以内、同步训练 verl / TRL 足够，别自研
    多机、需要 MoE + 异步 在 verl 上补 TITO 与双侧 IS，不必重写
    有超长轨迹（agent、1M 上下文） 需要 partial rollout + 微虚机，考虑自研或改 Kimi 的 AgentENV
    需要训推量化一致 必须有 QAT 支持；开源框架这块普遍弱
    需要多智能体并行（Agent Swarm） orchestrator 可训、subagent 冻结在中间 checkpoint，别端到端一起训
    团队 <5 人 用开源，把精力放在数据与环境上

    开源路线的现状：verl / TRL 的同步 DPPO / GSPO 实现已经够用，缺的是 TITO 接口、staleness 上界调度、QAT 支持三块——恰好是自研框架的差异化所在。判断标准不是"框架强不强"，而是"你缺的那块会不会卡住"。

    五、五个必须监控的指标¶

    1. 训推 logprob 偏差：同一批样本在 rollout 引擎与训练引擎上的 logprob 差，应接近 0。
    2. staleness 分布：看 P99，不看均值。
    3. clip 命中率：token 级被屏蔽的比例；过高说明策略漂移快。
    4. 环境失败率：因环境问题（非模型）失败的样本占比；超过 5% 先查环境。
    5. 有效样本率：一轮 rollout 中真正进入训练的样本比例。

    采集方式：每步在固定 replay 集上同时跑 rollout 与训练两个引擎的 forward，记录 logprob 差；staleness 与 clip 命中率在 batch 元数据里逐样本记，再聚合到分钟级。三个指标都该配告警阈值，而不是事后回看。
